What this site is

fridge.run is a static site on GitHub Pages, published from the repository root of LuckyMonkey/node-home. It is the public front door for fridge, a 2012 Mac mini running Ubuntu Server that serves DNS, ingress, chat and backup quorum for a home network.

What is real and what is not

Being explicit about this, because the previous version of the site blurred it.

ElementStatus
Dashboard metricsReal. Collected from the node by tools/collect-fridge-status.sh into status.json and committed. A snapshot, not a live poll — its age is displayed.
Service healthReal. Functional probes: each service is asked whether it answers, rather than asking Docker whether a container exists.
Video wallReal. Three clips in /media/warning-wall/. Kept deliberately.
The “Proceed” buttonNot authentication. A plain link. Nothing behind it is access-controlled.
Uploads / writesNot available. Static hosting cannot enforce identity.

Why there is no IAM yet

GitHub Pages serves static files and runs no server-side code. Any login implemented in client-side JavaScript can be bypassed by reading the page source, so it would be decoration rather than a control. Rather than ship that, the sign-in point is marked as a hook and left honest.

The three ways to get real identity

ApproachPublic readReal authTrade-off
Apps Script backendYesYes — Google verifies identity server-sideApps Script becomes the trust boundary
Served from the nodeNo — tailnet onlyYesNot reachable publicly
Reverse proxy on a VPSYesYesCosts money; another host to maintain

The node sits behind CGNAT, so it cannot accept inbound connections directly. Tailscale solves reachability for known devices, but Tailscale Funnel only serves its own *.ts.net hostname and cannot present a valid certificate for fridge.run — so Funnel alone cannot put this domain in front of the node.

Deployment

Pages is configured in legacy mode, publishing main at /. Push to main and it deploys. A previous workflow published ./docs and reported success on every run while being entirely ignored — editing docs/ appeared to work and changed nothing. That workflow has been removed so there is exactly one deployment path.
